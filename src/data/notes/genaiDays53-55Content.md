## 2. Why Embeddings?
Keyword search matches literal terms. Semantic search attempts to match meaning. A user may ask "How can I make my app faster?" while a useful document says "performance optimization techniques". Embeddings can place these texts near each other even though they share few words.

An embedding is a fixed-length numeric representation generated by a model. It is not a human-readable summary and does not guarantee that two texts are equivalent.

Typical uses:
- Semantic search over notes, PDFs, and knowledge bases.
- Retrieval-Augmented Generation (RAG).
- Duplicate or near-duplicate detection.
- Recommendation and clustering.
- Code and multimodal retrieval when supported by the model.

## 3. How Embedding Models Work
A text embedding model maps an input string to a vector:

\[
f_\theta(\text{text}) = \mathbf{v} \in \mathbb{R}^{d}
\]

Here, \(d\) is the embedding dimension. A model may produce 384, 768, 1,536, or another number of dimensions; the correct value depends on the chosen model. Higher dimension does not automatically mean better retrieval.

The model learns a representation space in which useful semantic relationships can be measured geometrically. The exact training objective varies: contrastive learning, paired text training, and other objectives are common.

Important distinction: an LLM generates tokens; an embedding model produces a vector. Some model families offer both capabilities, but the tasks and output contracts are different.

## 4. Choosing and Using an Embedding Model
Evaluate models on your domain rather than choosing only by popularity. Consider:
- Retrieval quality on representative queries and documents.
- Language coverage, including code-switching and multilingual text.
- Maximum input length and truncation behaviour.
- Vector dimension, latency, throughput, and cost.
- Hosting, privacy, licensing, and hardware requirements.
- Whether the model has separate query/document instructions or task modes.

Use the same compatible embedding space for indexed documents and queries. If you change to an incompatible model, re-embed and rebuild the index; vectors from unrelated spaces should not be compared directly.

For production, version the model name, revision, preprocessing rules, and chunking configuration alongside the index.

## 5. Vector Geometry and Similarity Metrics
A vector is a point in a high-dimensional space. Similarity search ranks stored vectors against a query vector.

**Cosine similarity** measures orientation:

\[
\operatorname{cos}(\mathbf{a},\mathbf{b}) =
\frac{\mathbf{a}\cdot\mathbf{b}}{\|\mathbf{a}\|_2\|\mathbf{b}\|_2}
\]

**Dot product** is \(\mathbf{a}\cdot\mathbf{b}\). When vectors are L2-normalized, dot product equals cosine similarity.

**Euclidean distance** measures straight-line distance:

\[
 d_2(\mathbf{a},\mathbf{b}) = \sqrt{\sum_i(a_i-b_i)^2}
\]

Do not mix up ranking direction: cosine and inner-product systems commonly rank larger values first, while L2 distance ranks smaller values first. Confirm the metric and normalization assumptions of the selected index.

## 6. From Documents to a Vector Index
A typical indexing pipeline is:

```text
Source files / database
        ↓
Parse and clean text
        ↓
Split into meaningful chunks
        ↓
Attach stable IDs + metadata
        ↓
Embedding model → vectors
        ↓
Vector index / database
```

Each record should preserve more than a vector. Keep the original chunk text, stable identifier, source, page or section, version, and access-control metadata. The vector locates candidates; the text is what you pass to the language model.

## 7. Chroma: Core Concepts
Chroma is an open-source AI data infrastructure with collections that store records for retrieval. A collection typically contains:
- A unique ID for each record.
- An embedding vector.
- Optional document text.
- Optional metadata.

A collection is the main unit you add to and query. Choose a naming scheme that reflects a corpus or tenant boundary. Do not treat a collection name as an authorization system; enforce access control in the application and database configuration.

Chroma can generate embeddings through a configured embedding function or accept supplied embeddings. It supports dense and other retrieval approaches as documented by the current release.

## 8. Chroma: Add and Persist Documents
Install in a virtual environment:

```bash
pip install chromadb
```

Minimal local example:

```python
import chromadb

client = chromadb.PersistentClient(path="./chroma_data")
collection = client.get_or_create_collection(name="placement_notes")

collection.add(
    ids=["os-001", "dbms-001", "ml-001"],
    documents=[
        "A process is an instance of a program in execution.",
        "Normalization reduces redundancy in relational databases.",
        "A validation set helps select model hyperparameters."
    ],
    metadatas=[
        {"subject": "OS", "source": "os.md", "day": 1},
        {"subject": "DBMS", "source": "dbms.md", "day": 2},
        {"subject": "ML", "source": "ml.md", "day": 3}
    ]
)
```

This example uses the collection's configured embedding function. For an externally generated embedding, pass vectors through the API's `embeddings` field and ensure dimensions match the collection/index configuration. `PersistentClient` is suitable for local learning; evaluate a server or managed deployment for multi-user production.

## 9. Chroma: Query and Metadata Filtering
A text query can be embedded by the collection's embedding function:

```python
results = collection.query(
    query_texts=["How does a process differ from a thread?"],
    n_results=3,
    where={"subject": "OS"}
)

print(results["ids"])
print(results["documents"])
print(results["metadatas"])
print(results["distances"])
```

`n_results` requests the nearest number of results (top-k). `where` filters metadata; `where_document` can filter document text using supported operators. Chroma supports logical combinations such as `$and` and `$or` in its filter syntax. Check the current API reference for exact operators and value types.

Filtering is not a replacement for authorization. First establish which records the caller is allowed to access, then constrain retrieval so private chunks cannot enter the prompt.

## 10. FAISS: What It Solves
FAISS (Facebook AI Similarity Search) is a library for efficient similarity search and clustering of dense vectors. It provides index structures for different scale, speed, memory, and accuracy requirements, with C++ and Python interfaces.

FAISS is primarily a vector-search library, not a complete document database. Your application normally maintains a mapping from FAISS integer IDs to text chunks and metadata, or stores that payload in a separate database.

Choose FAISS when you want low-level index control, local/in-process retrieval, and the ability to tune search algorithms. Compare persistence, filtering, metadata, and operational features separately before selecting it as a full RAG storage layer.

## 11. FAISS: Exact Search with Normalized Vectors
Install a compatible CPU build in your environment (the package availability can vary by platform):

```bash
pip install faiss-cpu numpy
```

Cosine-style ranking can be implemented using normalized vectors and an inner-product index:

```python
import faiss
import numpy as np

# Each row is one document embedding. Replace with real model output.
doc_vectors = np.asarray([
    [0.8, 0.2, 0.1],
    [0.1, 0.9, 0.2],
    [0.7, 0.1, 0.6]
], dtype="float32")

query_vector = np.asarray([[0.75, 0.18, 0.12]], dtype="float32")

faiss.normalize_L2(doc_vectors)
faiss.normalize_L2(query_vector)
index = faiss.IndexFlatIP(doc_vectors.shape[1])
index.add(doc_vectors)

scores, positions = index.search(query_vector, k=2)
print(scores)
print(positions)
```

`IndexFlatIP` performs exhaustive inner-product search. With normalized vectors, that ranking corresponds to cosine similarity. The returned positions are row positions, so keep an aligned array or mapping to recover chunk IDs and text.

## 12. FAISS Index Families and Trade-Offs
- **Flat indexes:** exact exhaustive search; simple baseline; compute grows with corpus size.
- **IVF indexes:** partition the vector space into lists and search selected lists; faster at scale but may miss neighbours if search parameters are too restrictive.
- **HNSW indexes:** graph-based approximate nearest-neighbour search; strong speed/recall trade-offs with memory and build-time costs.
- **Product quantization (PQ):** compresses vectors to reduce memory; introduces approximation error.

Start with an exact baseline on a manageable dataset. Introduce approximate indexing only after measuring latency and recall needs. Index parameters should be tuned on your workload, not copied blindly from a benchmark.

## 13. Top-k Retrieval
For a query vector \(q\), top-k retrieval returns the k highest-ranked candidates under the chosen similarity score, or the k lowest distances under a distance metric.

```text
Query → Embed → Similarity search → Rank candidates
                              ↓
                         Return top-k
```

Choosing k is a retrieval and context-budget decision:
- Too small: relevant evidence may be missed.
- Too large: irrelevant text, latency, and prompt cost increase.
- The useful k depends on chunk size, question type, corpus, and reranking strategy.

Use a validation query set to compare k values. Do not assume k=5 or k=10 is universally optimal.

## 14. Metadata Filtering Basics
Metadata describes a record independently of its semantic text. Examples:

```json
{
  "subject": "Operating Systems",
  "semester": 5,
  "source": "lecture-08.pdf",
  "visibility": "student",
  "updated_at": "2026-10-20"
}
```

Common filter dimensions:
- Subject, course, department, or document type.
- Date range or version.
- Language or content category.
- User, tenant, or access scope.

Use metadata to narrow a semantic search to a valid subset. Validate metadata types and normalise values at ingestion. Missing metadata keys may behave differently from explicit null values; test the exact database semantics.

## 15. Chroma vs FAISS
| Dimension | Chroma | FAISS |
|---|---|---|
| Main role | Vector data infrastructure | Vector similarity-search library |
| Stored payload | IDs, documents, metadata, embeddings | Primarily vectors and index structures |
| Metadata filtering | Built-in query filters | Usually implemented in application or via supported ID selectors |
| Index choices | Managed through Chroma internals/configuration | Explicit index-family selection and tuning |
| Good starting point | Small RAG app with convenient document records | Custom vector retrieval and index experimentation |

They are not always mutually exclusive. An application can use FAISS for vector search and a separate store for text, metadata, and permissions.

## 16. Retrieval Quality: Recall and Precision
**Precision@k** asks: among the k retrieved items, what fraction is relevant?

\[
\text{Precision@k}=\frac{\text{relevant retrieved items in top-k}}{k}
\]

**Recall@k** asks: how many of all known relevant items were retrieved?

\[
\text{Recall@k}=\frac{\text{relevant retrieved items in top-k}}{\text{all relevant items}}
\]

A high-recall retriever is less likely to miss evidence; a high-precision retriever returns fewer distractions. In RAG, retrieval quality should be evaluated separately from answer quality. Track both retrieval metrics and end-to-end grounded answer quality.

## 17. Common Failure Modes and Debugging
- **Wrong embedding space:** query/document vectors come from incompatible models or dimensions.
- **Poor chunking:** chunks split definitions from explanations or combine unrelated sections.
- **Wrong metric:** distance and similarity are interpreted in the wrong direction.
- **No metadata discipline:** missing or inconsistent fields cause filters to exclude useful records.
- **Stale index:** updated source files are not re-embedded or old chunks remain.
- **Top-k too low/high:** relevant context is missed or noise overwhelms the prompt.
- **No ID mapping:** retrieved vector positions cannot be mapped reliably to source chunks.

Debug by inspecting the raw query, embedding model/version, top-k texts, distances/scores, metadata, and source version before blaming the LLM.

## 19. Placement and Interview Questions
**Q1. What is an embedding?**
A fixed-length numeric representation produced by a model, designed so geometric relationships can support tasks such as semantic similarity and retrieval.

**Q2. Why use a vector database in RAG?**
It stores vectors and associated records and provides similarity retrieval so the system can select relevant chunks for a model's context.

**Q3. Cosine similarity vs Euclidean distance?**
Cosine compares vector orientation; Euclidean measures straight-line distance. The correct metric depends on model training and index configuration.

**Q4. What does top-k mean?**
Return the k best candidates according to the selected ranking metric.

**Q5. Chroma vs FAISS?**
Chroma offers a document-oriented vector data layer with metadata/query features; FAISS is a vector-search library whose application often manages payload and metadata separately.

**Q6. Why re-embed after changing embedding models?**
The new model may define a different vector space or dimension, so old and new vectors may not be directly comparable.

**Q7. How do you improve retrieval?**
Improve parsing/chunking, choose a suitable embedding model, tune metric and top-k, apply valid filters, add reranking, and evaluate on representative labelled queries.
